# RAG 生产级改造路线图

本文面向当前仓库 `my_rag_system`，目标不是重复通用的 RAG 最佳实践，而是基于现有实现给出一份可执行、可分期推进的生产化改造方案。

当前项目已经具备以下良好基础：

- 已有 API 服务与流式输出：`api_server.py`
- 已有混合检索、重排、压缩、拒答短路：`rag_engine.py`
- 已有文档切块与本地向量索引：`knowledge_base.py`
- 已有会话持久化与基础鉴权：`db/*`
- 已有离线评测与并发压测入口：`ragas/*`、`tests/concurrency/*`

这意味着项目已经越过“能跑”的阶段，接下来要解决的是“能稳定上线并持续演进”的问题。

## 1. 生产级的判断标准

一个生产级 RAG 系统，至少要同时满足以下 4 类目标：

1. **答得准**
   检索准确、引用可信、拒答可控、升级后不轻易退化。
2. **扛得住**
   并发、超时、异常、冷启动、索引重建、模型加载都可控。
3. **查得清**
   出现坏答案、慢请求、空结果时，能快速定位是检索、重排、Prompt、模型还是数据问题。
4. **管得住**
   文档、索引、配置、权限、审计、回滚都有明确治理方式。

如果只优化检索效果，而没有测试、监控、索引治理和安全策略，系统仍然只能算“工程化 demo”。

## 2. 当前项目的关键缺口

结合当前仓库结构，最主要的缺口如下：

### 2.1 测试与回归保护不足

- `tests/` 目前几乎只有并发压测脚本
- 缺少单元测试、API 集成测试、知识库构建测试、回归问答集测试
- 一旦调整 `chunk`、`rerank`、`SEARCH_K`、Prompt，很难自动判断是否退化

### 2.2 可观测性不足

- 缺少结构化日志、指标埋点、请求链路追踪
- 线上无法快速回答以下问题：
  - 检索命中了哪些文档
  - rerank 前后排序如何变化
  - 每一步耗时是多少
  - 哪些问题频繁拒答或无答案
  - 哪类问题成本过高

### 2.3 知识库与索引治理不足

- 当前更偏“本地单份 FAISS 索引 + 手工重建”
- 缺少文档版本、索引版本、增量更新、灰度切换、回滚机制
- 缺少删除文档后的索引一致性策略

### 2.4 多轮能力尚未真正闭环

- 会话消息已落库，但 `RAGEngine.ask()` 仍按单轮问题工作
- 当前多轮更像“UI 层有历史”，而不是“模型层真正理解上下文”
- 对追问、省略主语、上下文代词问题会有明显影响

### 2.5 安全与治理能力仍偏基础

- 现有能力主要是 API Key、Prompt 约束、离题短路
- 还缺少：
  - 文档上传校验
  - 敏感信息脱敏
  - Prompt 注入分级处理
  - 审计日志
  - 租户/部门隔离

### 2.6 评测体系还偏离线

- 已有 `RAGAS` 是很好的起点
- 但生产环境还需要在线反馈闭环：
  - 用户好评/差评
  - 人工纠错池
  - 高频失败问题池
  - 版本间 AB 对比

## 3. 改造原则

建议按下面 4 条原则推进，避免一开始把系统改得过重：

1. **先补底座，再冲效果**
   没有测试、日志、索引治理时，调优成果难以稳定沉淀。
2. **先保证可回退，再做激进优化**
   每次改 chunk、rerank、Prompt、模型前，先建立回归和版本切换能力。
3. **把“文档更新”当成正式流水线，不当成手工动作**
   生产系统的知识更新频率通常高于代码更新频率。
4. **优先解决“最容易线上出事故”的部分**
   比如超时、冷启动、错误定位、脏索引、多轮误答、越权访问。

## 4. 分阶段路线图

下面建议按 `P0 -> P1 -> P2` 三个阶段推进。

---

## 5. P0：先补上线底座

目标：把当前系统从“功能完整”提升到“可上线试运行”。

### 5.1 建立基础测试体系

优先补这些测试：

- `knowledge_base.py`
  - 文档加载是否成功
  - 父子切块是否符合预期
  - metadata 是否正确带出 `source`、`parent_content`
- `rag_engine.py`
  - 离题短路是否生效
  - 无检索结果时是否稳定拒答
  - rerank 开关前后是否能返回稳定结构
  - `answer_only` 与 `sources` 输出格式是否稳定
- `api_server.py`
  - `/health`
  - `/api/chat`
  - `/api/chat/stream`
  - 数据库开启/关闭时的行为差异

建议新增：

- `tests/unit/test_knowledge_base.py`
- `tests/unit/test_rag_engine.py`
- `tests/integration/test_api_server.py`

验收标准：

- 核心路径至少有一套可自动执行的测试
- 修改 Prompt、检索参数、API 响应结构时能第一时间发现回归

### 5.2 建立最小回归问答集

基于你的业务域，先整理一组高价值问题，建议至少覆盖：

- 直接事实问答
- 多条件问答
- 相似条款区分
- 应拒答问题
- 知识库外问题
- 多文档综合问题
- 易混淆对抗问题

建议落地为：

- `ragas/data/production_smoke_eval.json`

用途：

- 每次改参数、Prompt、模型、chunk 策略后跑一遍
- 不追求一次覆盖所有问题，但要覆盖最容易出事故的业务问题

### 5.3 增加结构化日志

建议给每次请求记录统一字段：

- `request_id`
- `conversation_id`
- `user_id`
- `question`
- `off_topic_hit`
- `retrieved_count`
- `rerank_enabled`
- `rerank_top_sources`
- `llm_model`
- `latency_ms`
- `error_type`

重点位置：

- `api_server.py`
- `rag_engine.py`
- `knowledge_base.py`

验收标准：

- 单次坏答案能通过日志还原出“问题 -> 检索 -> 重排 -> 生成”链路

### 5.4 增加超时、异常分级和兜底

当前链路里最容易线上出问题的是：

- 向量索引加载失败
- reranker 模型冷启动过慢
- 外部 LLM 超时或返回异常
- SSE 中途断流
- 文档解析失败

建议补充：

- 统一错误码与错误响应结构
- 外部 LLM 请求超时配置
- SSE 结束事件与异常事件规范
- 索引未就绪时的清晰错误信息
- 冷启动阶段的 readiness 区分

重点文件：

- `api_server.py`
- `rag_engine.py`
- `config.py`

### 5.5 增加分环境配置

建议至少分为：

- `dev`
- `test`
- `prod`

需要梳理的配置项：

- 模型路径
- API key
- DB 地址
- `SEARCH_K`
- `RERANK_TOP_N`
- `RAG_LLM_MAX_TOKENS`
- CORS
- 日志级别

重点文件：

- `config.py`
- `.env`
- `README.md`

### 5.6 P0 完成标准

满足以下条件即可进入 P1：

- 核心 API 有自动化测试
- 有一套最小回归问答集
- 请求链路有结构化日志
- 关键异常可识别、可定位、可兜底
- 有清晰的开发/生产配置边界

## 6. P1：补齐可运维与可治理能力

目标：把系统从“可上线试运行”提升到“可稳定维护”。

### 6.1 建立知识库更新流水线

当前建议把“文档更新 -> 解析 -> 切块 -> 建索引 -> 切换”显式流程化。

建议引入：

- 文档版本号
- 索引版本号
- 索引元数据文件
- 构建时间与构建来源记录
- 构建成功后再切换当前服务使用的索引

推荐设计：

- `faiss_index/<index_version>/...`
- `db/` 或元数据文件记录当前激活版本
- 新索引构建成功后做原子切换

重点模块：

- `knowledge_base.py`
- `api_server.py`
- 可新增 `scripts/rebuild_index.py`

### 6.2 支持增量更新与回滚

至少需要明确：

- 新增文档如何入库
- 删除文档如何从索引移除
- 文档更新时是否全量重建
- 索引升级失败后如何回退到上一版

短期建议：

- 即使先不做“真增量索引”，也要先支持“版本化全量重建 + 原子切换 + 一键回滚”

### 6.3 接入基础监控指标

建议至少输出以下指标：

- QPS
- P95/P99 延迟
- 错误率
- 拒答率
- 无来源答案占比
- 每次请求平均召回数
- rerank 平均耗时
- LLM 平均耗时

可以先从日志聚合开始，再接 Prometheus 或其他监控系统。

### 6.4 强化数据库与状态治理

当前 MySQL 已经用于会话持久化，下一步建议补充：

- 索引版本表
- 文档元数据表
- 用户反馈表
- 审计表

如果未来有多租户需求，建议尽早考虑：

- `tenant_id`
- 文档按租户隔离
- 检索按租户过滤
- 会话按租户归属

### 6.5 容器化与部署规范

建议补充：

- `Dockerfile`
- `.dockerignore`
- 启动探针与健康检查说明
- 模型目录挂载说明
- 索引目录挂载说明

重点是让部署具备一致性，而不是只依赖本机环境。

### 6.6 P1 完成标准

- 文档更新有标准流程
- 索引可版本化、可切换、可回滚
- 服务有基础指标监控
- 数据库结构能承载治理与反馈
- 部署方式可复制、可迁移

---

## 7. P2：补齐产品质量与高级能力

目标：把系统从“稳定服务”提升到“高质量业务系统”。

### 7.1 真正做多轮上下文理解

当前建议不要直接把整段聊天历史塞进 Prompt，而是分层做：

1. 最近轮次摘要
2. 当前轮 query rewrite
3. 必要时把历史问法转成检索增强上下文

推荐演进路径：

- 先做追问改写
- 再做对话摘要
- 最后做长期会话记忆

重点模块：

- `api_server.py`
- `rag_engine.py`
- `db/chat_store.py`

### 7.2 建立线上反馈闭环

建议增加：

- 点赞/点踩
- “答案无帮助”原因分类
- 人工修正答案入口
- 高频失败问题池

这样后续优化不再只靠主观体验，而是能基于真实用户问题迭代。

### 7.3 强化安全策略

建议从以下几层补：

- 输入层
  - 问题长度限制
  - 恶意模式识别
  - 上传文档类型校验
- 检索层
  - 按权限过滤文档范围
- 生成层
  - 对敏感问题和高风险问题分级策略
- 审计层
  - 记录谁问了什么、系统答了什么、引用了哪些文档

### 7.4 提升答案可信度

建议后续逐步补齐：

- 引用片段高亮
- 答案句子级引用
- 无依据时强拒答
- 答案置信度或风险标记

### 7.5 建立版本对比评测

生产迭代中建议把以下变更都纳入版本对比：

- Prompt 变更
- chunk 策略变更
- reranker 变更
- embedding 模型变更
- LLM 变更

每次变更至少比较：

- RAGAS 离线结果
- 生产 smoke 集结果
- 在线用户反馈
- 时延与成本变化

### 7.6 P2 完成标准

- 多轮问题显著优于单轮
- 真实用户反馈可驱动优化
- 高风险问题有明确处理策略
- 版本升级能做质量、延迟、成本三维对比

## 8. 建议的代码级落点

下面给出一个更贴近仓库的模块映射。

建议承担：

- 文档清洗标准化
- 切块策略测试化

### `api_server.py`

建议承担：

建议承担：

- 单元测试

## 9. 推荐执行顺序

如果按性价比排序，我建议你这样推进：

1. 先做 `P0.1 + P0.2 + P0.3`
   也就是测试、最小回归集、结构化日志。
2. 再做 `P0.4 + P0.5`
   也就是超时兜底、分环境配置。
3. 然后进入 `P1.1 + P1.2`
   先把索引版本化和回滚打通。
4. 再做 `P1.3 + P1.4`
   把监控和治理数据结构补齐。
5. 最后推进 `P2`
   重点做多轮、反馈闭环和安全增强。

这条顺序的核心原因是：

- 没有回归和日志，后续优化容易“越改越乱”
- 没有索引治理，知识库一更新就容易线上出事故
- 多轮和高级能力虽然重要，但不应先于底座建设

## 10. 一份务实的里程碑建议

如果按三周到六周节奏推进，可以参考下面的切分：

### 里程碑 1

- 建立测试目录结构
- 补 `/api/chat` 和 `rag_engine` 基础测试
- 固化一套 smoke 问答集
- 加结构化日志

### 里程碑 2

- 加统一错误边界
- 加超时和冷启动状态管理
- 梳理生产配置
- 输出基础部署文档

### 里程碑 3

- 做索引版本化
- 做全量重建与原子切换
- 做回滚入口
- 增加文档与索引元数据

### 里程碑 4

- 做用户反馈闭环
- 做多轮 query rewrite
- 做安全分级和审计
- 做版本对比评测

## 11. 下一步最值得立即动手的事项

如果只选 3 件最值得立刻开始的事，我建议是：

1. 建立 `tests/unit` 和 `tests/integration`
2. 增加请求级结构化日志
3. 设计“索引版本化 + 原子切换”方案

这三件事能最快把系统从“功能完成”拉到“可持续维护”。

## 12. 结论

对当前项目来说，生产级改造不是单纯的“再调检索效果”，而是一次从 RAG 功能实现走向服务治理的升级。

最重要的不是继续堆新能力，而是先让现有能力变得：

- 可测试
- 可观察
- 可回退
- 可治理

在这之后，再做多轮、反馈闭环、权限隔离和高级安全策略，投入产出会更高，系统也更稳。
